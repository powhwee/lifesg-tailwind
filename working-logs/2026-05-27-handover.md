## Intro-content audit — LifeSG vs ours

### What to compare

LifeSG's per-component MDX has a consistent intro shape. Sample from
`stories/accordion/accordion.mdx`:

```mdx
# Accordion

## Overview

Displays expandable and collapsible content panels that can be
toggled by the user.

```tsx
import { Accordion } from "@lifesg/react-design-system/accordion";
```

<Canvas of={AccordionStories.Default} />

## Smaller Accordion item titles

Specifying the type in the `Accordion.Item` produces a smaller text
size for each item's title.

<Canvas of={AccordionStories.SmallAccordionItemTitle} />
...
## Accessibility
...
## Component API
<PropsTable />
```

Recurring elements in LifeSG MDX:

1. **`## Overview`** — single sentence, "what this component does"
2. **Import** as a fenced code block right after Overview
3. **`<Canvas of={…Default} />`** before any variant prose
4. **Per-variant section** — short prose intro + canvas, prose explains
   "use this when…" / "set X if Y" / "without Z, …"
5. **Accessibility** — prose + code examples, often a dedicated
   `<Canvas of={Accessibility} />` story
6. **Component API** — `<PropsTable />` (their custom component;
   we use `<Controls of=>`)

### What ours generally has

Our MDX shape (e.g. `src/components/ui/accordion.mdx`):

- One-paragraph intro after the title (no explicit `## Overview` header)
- Import via `<Source language="tsx" code={…} />` (renders the same as
  a fenced block — different syntax, same output)
- Per-variant canvases under variant section headers — but the prose
  per variant is **often missing** (we just have the heading + canvas)
- Accessibility section — present on most but not all components;
  prose varies in depth
- Props via `<Controls of={…} />` — same idea as their PropsTable
- Notes section — implementation quirks, token references,
  cross-component pointers (LifeSG does NOT have this; it's our value-add)

### Suggested scan procedure

For each of our 53 component MDX files, compare against the
corresponding LifeSG MDX and identify:

1. **Missing per-variant prose** — we have a heading + canvas but no
   explanation of when to use that variant. Easy win — port the
   one-sentence intros LifeSG ships.
2. **Thinner overview** — our opening paragraph vs theirs.
3. **Missing accessibility recipes** — LifeSG often ships code
   examples (e.g. Accordion's `headingLevel` example). We document
   accessibility as bullet points; missing the code-example angle.

**Things to preserve** (do NOT port):

- **Our API separation** — we keep `comp.stories.tsx` + `comp.mdx`
  with embedded `<Canvas of=>`. Don't move to LifeSG's "single MDX
  with inline JSX" style.
- **Our Notes section** — implementation context that LifeSG
  doesn't ship is useful for ramping up.
- **System-tour split** for layout/typography/divider — LifeSG's
  Foundations follows a similar split; ours mirrors it correctly.
- **Foundations paired MDX + story** (post `9692a2c`) — the prose +
  panel separation works; preserve it.

## Controls panel — misleading on variant stories

### What the user sees

Open any multi-variant tour story — e.g. `Selection and input / Icon /
Sizes` — and the Controls panel shows `as*`, `size`, `tone`. Flip `size`
to `xl` or `tone` to `error`. **Nothing in the canvas changes.** The
panel looks broken; it isn't.

### Why

Stories like `Sizes` / `Tones` / `Gallery` / `StyleTypes` use a custom
render that hardcodes per-instance props:

```tsx
export const Sizes: Story = {
  render: () => (
    <Row gap={6}>
      <Icon as={Check} size="xs" />
      <Icon as={Check} size="sm" />
      <Icon as={Check} size="md" />
      <Icon as={Check} size="lg" />
      <Icon as={Check} size="xl" />
    </Row>
  ),
};
```

`render: () =>` takes **no args**, so Storybook re-runs the render with
fresh args from the panel but the hardcoded props win. The panel
shows controls because meta declares the argTypes; that's what's
misleading.

Stories using `args: { … }` (or `render: (args) => <Comp {...args} />`)
do work correctly with controls — the `Default` story on every
component is interactive.

### Scope

`grep -rl "render: () =>" src/components/ui/*.stories.tsx` returns 37
files; rough estimate is 80–100 individual story exports that exhibit
this. Foundations stories (`src/components/foundations/*.stories.tsx`)
already disable controls at meta level (`parameters.controls.disable:
true`); this is only an issue for component stories.

### Options (pick one for next session)

| Option | What | Trade-off |
|--------|------|-----------|
| **A. Sweep all stories** | Add `parameters: { controls: { disable: true } }` to every story whose `render` doesn't take args | One mechanical batch commit (~80–100 edits). Establishes a clear convention going forward. Variant stories signal "fixed demo, not interactive". |
| **B. Sample first, decide later** | Apply the fix to one component (e.g. Icon) so you can see the result in Storybook; then commit to full sweep or revisit | Lower risk; lets you eyeball the UX before committing to a sweep. |
| **C. Convert variants to args-driven** | Rewrite stories like `Sizes` into multiple single-instance stories (e.g. `SizeXS`, `SizeSM`, …) each driven by args | Heavier refactor. Loses the visual "all sizes at once" scale-tour pattern — that's the whole point of the variant story. **Not recommended** for tour-style stories. |
| **D. Leave + document** | Note the quirk in component MDX so users know which stories are interactive | Cheapest. Users still hit confusion before reading the note. |

**Recommended:** A (full sweep), with the convention added to the
"Conventions established" table below. The fix is mechanical
(`Edit` with `replace_all: false` per file) and the result is a
sidebar that visually signals interactive vs. fixed-demo stories.

### Convention to encode (whichever option chosen)

> Stories using `render: () =>` (no-args render) MUST set
> `parameters: { controls: { disable: true } }`. Stories using
> `args: { … }` or `render: (args) => <Comp {...args} />` leave
> controls enabled.

Add to "Conventions established this session" once decided.

## Open issues / pitfalls reinforced

- **SB10 indexer state-drift** — adding new MDX / stories while
  `storybook dev` is running often corrupts the in-memory index
  (`/index.json` returns 500). Restart is the only fix. Build is fine;
  it's just the dev-server hot-reload that breaks.
- **MDX `{...}` is JSX-expression** — wrap descriptive placeholders
  in inline backticks. Captured as `mdx-curly-braces-escape` memory.
- **MDX tables need remark-gfm** — already wired (commit `7d4d03d`).
  If you see literal `|` in a docs page, check `.storybook/main.ts`.
- **Probe scripts are throwaway** — pattern is create →
  `node .check-tmp.mjs` → delete in the same batch. Don't commit them.
  Use `playwright/test`'s `chromium` from project root so module
  resolution works.

## Architectural review — LifeSG v3.x / v4 vs Tailwind port

Produced during this session. Full write-up in
`working-logs/2026-05-27-nextjs-lifesg-vs-port-comparison.md` with a side-by-side
HTML visualisation in `working-logs/2026-05-27-form-comparison.html`. The original
design system review is in `working-logs/2026-05-27-design-system-review.md`.

### Key findings

1. **v3.x tokens are JavaScript functions**, not CSS variables. Every
   colour/spacing/motion token is `(props: StyledComponentProps) => string`
   — resolved at runtime from `props.theme`. v4 moves these to CSS
   variables (`--fds-*`), which is a performance improvement but does
   not remove the `styled-components` dependency.

2. **Developer-facing code is identical between v3.x and v4.** The
   component API (`Form.Input`, `Button.Default`, etc.) is the same.
   The v4 changes are internal to the design system package.

3. **Total code a feature developer writes is roughly the same** across
   LifeSG and the Tailwind port. The difference is file distribution:
   static content (navbar, footer, headings) moves from a `'use client'`
   file to server files (`layout.tsx`, `page.tsx`). Only ~8 lines
   (the `LifeSGProviderWrapper`) genuinely disappear.

4. **The practical difference is where `'use client'` falls.** LifeSG's
   `styled-components` dependency pulls static content into the client
   boundary. The Tailwind port allows the boundary to be drawn narrowly
   around components that require client-side state (forms, modals).

5. **Data fetching is identical** in both approaches — `async` Server
   Component in `page.tsx`, unrelated to the styling library.

### Form.X convenience wrapper gap

LifeSG ships `Form.Input`, `Form.Select`, `Form.DateInput`, etc. —
20+ one-liner wrappers that bundle label + input + error + layout.

The port uses composable `Field` + `Input` (2 components per field).
The total props are the same; the developer writes `Field` wrapping
the input instead of a single `Form.Input`. This is the **only**
component pattern where the port requires more nesting than LifeSG.

All other component categories (Card, Drawer, Accordion, Tab, Navbar,
Footer) use the same sub-component structure in both systems.

The README documents this as intentional (Pillar 2 — Hybrid Field +
Form.X) and notes that thin `Form.X` wrappers (~10 lines each) can
be added when the convenience is needed.

### Modal sub-component gap

`modal.tsx` is missing `Header`, `Body`, `Footer` sub-components.
`modal-v2.tsx` already has `Content` and `Footer`. The older
`modal.tsx` should either be updated to match or deprecated in
favour of `ModalV2`.

Drawer and Card already have full sub-component sets — this gap is
specific to the older Modal.

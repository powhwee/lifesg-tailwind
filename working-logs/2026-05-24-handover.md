### Round 2 — "Radio still looks different" (`34700b6`)

User pinged with a high-zoom screenshot: ours `size-6` radio still read smaller than LifeSG. I re-checked LifeSG's SVG path geometry and realized I'd previously read only the *inner-fill* portion (coords ~6..14 = ~22.4px). ### Round 3 — Diagnosis: rendering primitive mismatch (`d3df5b5`)

User pinged again. "Why has this been so elusive to fix, are we whacking mole again?"

Honest diagnosis: I was treating this as a *sizing* problem when it was actually a *rendering-primitive* problem.

LifeSG renders checkbox + radio chrome as **SVG icons** (`SquareIcon`, `CircleDotIcon` from `@lifesg/react-icons`). One path draws both outer ring AND inner fill, integrated, with anti-aliased curves. Ours rendered as **CSS border + inner span**: a hard-edged border around a positioned colored dot. These two methods produce visibly different results even at identical nominal dimensions — uniform border vs tapered SVG stroke, edge anti-aliasing differs, corner treatment differs, outer-to-inner gap controlled differently.

Every `size-X` / `border-X` tweak chased a visual that *emerges from* a different rendering method. The whack-a-mole was structural.

The parity-principle escape: Lucide is our project's chosen icon vocabulary (~30 icons across the codebase). LifeSG's `@lifesg/react-icons` is the outlier *within OUR design language*. Per "Match the language, not the layout," the right move was to switch our chrome to Lucide and document the diff as DESIGN-LANGUAGE.

Refactored both:
- Radio chrome: Lucide `<Circle>` (unchecked) / `<CircleDot>` (checked)
- Checkbox chrome: Lucide `<Square>` (unchecked) + filled bg + `<Check>` / `<Minus>` (checked / indeterminate, the hybrid pattern was already present)
- Restored `size-8 / size-6` (LifeSG box-model — clean measure-* story, no VISUAL-PARITY allowlist needed)
- Added DESIGN-LANGUAGE row to `docs/parity-principle.md`

### Round 4 — "Nipples" + ring one step too big (`cec043f`)

Two issues surfaced from Round 3:

1. Lucide's `CircleDot` has its inner dot proportionally tiny — user described as "nipples." Composed `<Circle>` + CSS `<span>` for the inner dot so we control the proportions.
2. Ours at `size-8 / size-6` filled the full container with the Lucide outline — one Tailwind step bigger than LifeSG's visible SVG ring (~25.6px in their 32px container).

Shrunk to `size-7 / size-5` (28 / 20). Re-added VISUAL-PARITY allowlist entries — but this time with the principled framing (chrome rendered by Lucide; container sized to LifeSG visible disc; box-model gap documented).

### Round 5 — Checkbox-specific shrink (`28bb3d7`)

Radio at `size-7` read perfectly. Checkbox at `size-7` still read one step too big. Why?

LifeSG's checkbox SVG path occupies less of its viewBox (~14/20 = 70%) than the radio's outer ring (~16/20 = 80%). So at the same container size, Lucide's `Square` (which fills its viewBox more aggressively than LifeSG's `SquareIcon`) overshoots LifeSG's visible checkbox by more than the radio overshoots LifeSG's visible ring.

Shrunk *checkbox only* one more step: `size-6 / size-4` (24 / 16). Radio stayed at `size-7 / size-5`.

Documented: checkbox tracks one step smaller than radio for visible-disc parity. This is now in `docs/parity-principle.md` and `[[selection-input-indicator-convention]]`.

### Sub-pixel artifact (accepted, not fixed)

User noticed the inner radio dot in row 2 of the demo appears slightly off-center. DOM probe confirmed it's mathematically centered (Δ=0.00 for both Lucide SVG ring and CSS span dot). The artifact is intrinsic: the row-2 radio sits at fractional x-position (~466.44px — depends on preceding label glyph widths in the flex row), and the browser anti-aliases SVG strokes and CSS borders differently at sub-pixel boundaries. SVG anti-aliasing is symmetric around the path; CSS rounded-edge anti-aliasing is asymmetric in some renderings.

Accepted as a known limitation. Real consumer code with different label widths rarely sits at the same fractional boundary; the artifact will often vanish. The "principled" fix would be to render the dot as a child SVG inside the Lucide `<Circle>` so anti-aliasing is uniform, but that's diminishing-returns complexity.

## Iteration lessons (what I'd do differently)

1. **Diagnose the rendering primitive first, then size.** I spent four iterations changing `size-X` / `border-X` before realizing the issue was CSS-border vs SVG-stroke. The very first fix should have been "what is LifeSG actually drawing, and with what primitive?" — then choose ours to match the primitive, then tune size.

2. **Read SVG paths in full, not in `slice(0, 400)`.** My early probe truncated the path data, so I extrapolated the outer-ring coords from incomplete info and pinned `size-6` to the wrong number. The path describes the OUTER ring at coords ~2..18 (visible ~25.6px), not the inner-fill at ~6..14 (~22.4px).

3. **"What was our principles?" is the right question to interrupt a loop.** The user asking me to recap the parity principle three rounds in is what un-stuck the conversation. The principle was sitting there the whole time ("match the language, not the layout — when LifeSG is the outlier within our design system, override") — I just needed to apply it to icons instead of only to sizes / padding / colors.

4. **Sub-pixel rendering can produce real-looking bugs that aren't bugs.** Always probe DOM-level centroids before chasing a visual centering issue.

## Pitfalls reinforced

(Carrying forward from 2026-05-23 + adding this session's.)

- **Library measured size ≠ library visible size.** Probing `getBoundingClientRect` returns the container; the eye reads the SVG path coverage inside it. Both matter; allowlist when they disagree.
- **Side-by-side visual review IS the test.** measure-* values can match while visual weights diverge.
- **Stale allowlist reasons mask new regressions.** Re-state after every sweep. Today's allowlist went through three re-statements (size-6 → size-7 → size-6/size-7 split) as the implementation evolved.
- **"Same shape, different rendering primitive" is the kind of mismatch that won't yield to size tweaks.** Match the primitive first.

## What was discovered (the data-token meta-bug)

`scripts/measure-content.mjs` reads `[data-token]`-marked elements and compares computed style between ours and LifeSG panes. The convention assumed `data-token` would mark the **widget under comparison**. But in 19 of 23 demos across content + core + navigation, `data-token` was placed on the `<code>` *label* element ("default" text, etc.) — not the widget.

Result: the measure script was comparing two ~16×50px text labels (obviously identical) and reporting "✓ match", while the actual widget chrome could diverge by hundreds of pixels.

**Concrete example**: `uneditable-section default` reported "✓ match" for the entire pilot's run. After moving `data-token` to the widget wrapper, the actual measurement was:
- ours: 324px tall, padding 24px uniform, radius 8px, label 12px bold, value 14px
- LifeSG: 622px tall, padding 32px/0 + 48px on inner, radius 0px, label 16px regular, value 16px

Effectively a different widget. The L5 screenshot the user spotted made this immediately obvious; the measure-content "passing" status had been hiding it.

Fixed in commits `82734c4` (content demos) + `e1192b4` (core + navigation demos). All 19 affected files relocated; `data-token` now consistently marks the comparable widget.
